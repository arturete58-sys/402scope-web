What a fault rate upper bound is

A provider with no faults in 34 observations has not proven it never fails. The upper bound is the worst fault rate consistent with what has been observed, at 95% confidence (Wilson interval). It is what a policy can sit on while a provider is still new. It is not an estimate of the provider’s rate.

Two providers at n=34, one with zero faults and one with five, return bounds of 10.2% and 30.1%. A buyer that holds anything above 15% holds the second from day one.

published

n ≥ 100. Confidence established; the figure can be cited.

provisional

n from 20 to 99. Low confidence: enough to support a policy, not to publish a rate.

insufficient_data

n below 20. No rate, but the bound is still returned.

402Scope Trust

From a measurement to a payment decision

Measurements are only useful if an agent acts on them before it pays. 402Scope Trust puts the scores where the payment is decided: in a Soroban contract on Stellar, and in the agent’s own wallet.

Running end to end on Stellar testnet

01 · Attest

Bonded attesters, onchain

Independent attesters lock a bond, make real paid calls and publish scores per endpoint and per seller in a Soroban registry. Each score commits to a Merkle root of the calls behind it, and the contract checks any call against it. A false score can be slashed.

02 · Enforce

A wallet that refuses untrusted sellers

An OpenZeppelin smart account with the 402Scope trust policy checks the seller inside its own authorization. Payments to sellers its chosen attesters do not trust fail to sign, whatever the agent’s code does.

03 · Any facilitator

No facilitator lock-in

The agent wallet paid through OpenZeppelin’s hosted Built on Stellar facilitator unchanged. Any x402 facilitator can add trust hooks to flag or refuse payments, rank its Bazaar listing, and share its listing with the observatory.

Delivery declarations

One vocabulary for what a buyer gets

x402 standardised how a seller asks to be paid, not what the buyer receives. 99.84% of resources declare the shape of their response; few declare anything about its quality, and those that do use six incompatible vocabularies.

402Scope publishes one: freshness, quality and provenance, carried by x402 itself as an extension. A seller is held only to what it declared, and only a breach of its own declaration is its fault.

  • Terms in the 402 challenge. extensions.declarations states what the seller commits to before payment, such as a maximum data age, and what it does if it breaks that.
  • A declaration per response. The X-402-Declaration header states the age and source of this response, and the seller’s delivery receipt signs it with the body.
  • Two tiers. In-band, usable and providerAtFault let a settlement layer skip or credit one charge. Out-of-band, the observatory’s fault rate bound tells a seller policy when to stop selling a provider that is honest but consistently broken.
  • Sellers that never adopt it are still read through the x402-declarations adapters, labelled as declared or inferred.

API

No key, no registration

60 requests per IP per 5 minutes; a batch of 50 counts as one. Every response that carries a rate carries the bound, n and the window it rests on.

GET  /v1/provider?endpoint=<url>    signed aggregate for one provider
POST /v1/providers                  {"endpoints":[...]}, up to 50
GET  /v1/endpoints                  what is currently measured
GET  /v1/history?endpoint=<url>     the series, with the rule changes in it
GET  /v1/coverage                   what is covered, by layer
POST /v1/verify                     check a third party's signed attestation
POST /v1/watch                      alert me when a provider crosses a bound
POST /v1/report                     contribute counts from a facilitator
GET  /v1/market                     market size, by chain, each with its criterion
GET  /v1/unused                     endpoints that answer but nobody pays
GET  /v1/latency                    measured settlement latency, with a suggested timeout
GET  /v1/health                     whether this observatory is working

Method

Everything is reproducible

Block ranges, ledger ranges, thresholds and criteria are published. Every figure in a report ships with the query that produces it.

  • The observation table is append-only. A database rule prevents modification of historical records. When a rule changes, the change is logged with an explicit scope declaring which observations it invalidates.
  • Aggregation has a floor. Fault rates are published above n=100 with a Wilson interval. Below that the API says so rather than returning a number that cannot be defended.
  • Local canaries with known-bad behaviour run alongside the real panel, so a silent failure of the instrument itself is detectable.
  • Nothing is charged to the providers measured. The observatory has no commercial relationship with any provider in its panel. Scores are never for sale.
  • Corrections. Figures later found wrong are corrected in public, including the ones that were more flattering before they were wrong. One correction withdrew a whole table rather than restate it; another was about the correction machinery itself failing. All corrections.
  • Right of reply. Any provider named in any report is contacted before publication and may submit a response, published unedited alongside the data concerning them.
  • Facilitators can contribute. A facilitator can share its Bazaar listing and the resources it settles, so coverage reaches providers no catalogue lists. Contributions add resources to measure; they never change a result.
